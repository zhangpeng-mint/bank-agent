# 架构决策总结

本文件独立汇总主要技术决策、放弃方案与演进条件。具体设计以 `01`–`08` 文档为准。

| 决策 | 当前选择与理由 | 当前放弃的替代 | 演进触发条件 |
|---|---|---|---|
| Agent 形态 | 单一显式编排器 + 专业确定性工具；易审计、上下文不重复 | 多 Agent 自由协作 | 大仓库并行任务可独立验收且评测证明收益 |
| 应用架构 | 模块化单体，CLI/API/MCP 共用应用核心 | 一开始拆微服务 | 团队、多主机、独立扩缩容或隔离要求明确 |
| 工作流 | 普通 Python 状态机 + SQLite checkpoint | MVP 直接使用 LangGraph | 需要复杂分支、长任务恢复和频繁人审暂停 |
| 主存储 | SQLite 单文件、单写多读 | PostgreSQL/图数据库 | 并发写入、数据规模或图查询复杂度超过基准 |
| 文档检索 | 精确匹配 + FTS5/BM25 + 关系扩展 | 默认向量库、Elasticsearch、RAGFlow | 回归集量化证明语义召回不足或进入团队规模 |
| 向量检索 | 暂缓，本地可插拔 | 云向量库 | 有授权、模型稳定、收益超过重建和泄露成本 |
| Java 分析 | rg 召回 + Tree-sitter 结构化 + 框架规则 | 仅正则；一开始全量 JavaParser | 符号解析误差是主要瓶颈时引入 JavaParser sidecar |
| 调用图 | SQLite typed nodes/edges，事实/观察/推断/未知分离 | 直接让模型读长代码；立即用 Neo4j | 图规模和多跳查询证明确需专用图引擎 |
| 知识源 | Git Markdown + 原文件 hash/派生文本 | 直接把 Word/PDF 当唯一知识库 | 若已有权威 DMS，则以 connector 同步但仍保留 snapshot |
| 服务入口 | CLI 优先；FastAPI/MCP 为薄适配器 | 重 Web UI | 多用户协作、审阅和权限运营需要 UI |
| MCP | 共享只读服务与统一索引，聚合为 4 个工具 | 每个动作一个工具、每客户端建索引 | 高频独立用例再拆工具；远程化后加入 OAuth/TLS |
| 模型 | 可插拔网关；无授权时模板/本地模型 | 把云模型作为硬依赖 | 组织审批数据类别、区域、保留与训练策略后 |
| 可追溯性 | 所有事实 claim 绑定程序生成 evidence ID | 仅在正文附自然语言“来源” | 不变；未来只增强签名和审阅流程 |
| OpenTelemetry | 非 MVP；先支持已有关联 ID/日志 | 假设现有系统已有完整 tracing | 非生产验证成功、系统 owner 批准插桩后渐进接入 |
| 写操作 | MVP 完全只读 | 自动修改、运行测试、连生产库 | 隔离环境、精确审批 token、审计和回滚全部到位 |

## 不可妥协的约束

1. 未经授权的银行内部资料不得发送给云模型。
2. 第一阶段不连接生产数据库，不修改业务代码。
3. 报告的“已确认事实”必须有可验证出处；模型推断永不自动升级为事实。
4. 索引、报告和运行证据必须固定到明确版本/snapshot。
5. 动态路由、反射、多实现和配置缺失必须显式呈现为歧义或未知。

## 推荐实施顺序

先做证据模型和合成回归集，再做 FTS5 文档检索；随后做 rg/Tree-sitter 代码图；最后接需求编排和 MCP。准确性由真实脱敏历史需求驱动，而不是以增加组件或模型调用次数驱动。
